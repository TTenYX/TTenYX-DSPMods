## 0. 一句话结论

**旧模型"一格 x = 常数弧长"在跨纬度带图上把赤道端算小 1.47 倍（根因，保留）；上一版为了堵这个洞改成"枚举全部合法粘贴姿态 × 0.05° 纬度格取最坏值"，把判据变成了"在任何合法纬度上都不能超限"，于是单区域整球图几乎找不到可用纬度、省带量被压到 0，同时搜索量爆炸导致掉帧（第二、三条不满）。**

**本版改成：用粘贴工具给出的本次锚点位置与朝向，逐节点按游戏自己的分段表算真实弧长，一次 O(节点数) 算清。** 3000 条带的蓝图整条省带流程 **≤ 135 ms**（含蓝图库场景的纬度选择），且所有蓝图 **越限新链节 = 0、分拣器空端 = 0、悬空引用 = 0**。

## 2. 长度模型（铁律①的技术保证）

对每个节点：

```
refLat(根) = 粘贴锚点纬度（粘贴工具 dotsSnapped[0] 的纬度）
refLat(子) = refLat(父) + sign · anchorLocalOffsetY(子) · 0.36°
节点纬度   = clamp(refLat + sign · 纬度轴偏移 · 0.36°)
经度差     = ∫(x_a → x_b) LonRadPerGrid(采样点纬度) dx      ← 两点之间积分，不取模
lpos       = GetDir(refLon + lonSign · 经度轴偏移 · LonRadPerGrid(节点纬度), 节点纬度) · (z·1.3333 + 0.2 + realRadius)
判据       = (lpos_b - lpos_a).sqrMagnitude > 5.3           ← BuildTool_BlueprintPaste ≈2087 行同一个判据
```

其中 `LonRadPerGrid(θ) = 2π / (PlanetGrid.DetermineLongitudeSegmentCount(round(θ/0.36°)−1 的绝对值 /5, 200) · 5)`。

### 本轮被数据证伪的假设（都在我自己的实现里，已修）

1. **"x × 区域参考纬度处的格宽"就够** —— 证伪。游戏用的是**该节点纬度**的格宽。实测 6k 在赤道锚点下，`x≈599.39` 上两个相邻点（Δx=0.0001）被算成相隔 175°、距离虚报 **391 m**；那条假链节又触发"越限邻域固定"与合并拒绝。
2. **"x × 该节点纬度处的格宽"就够** —— 证伪。`GetLongitudeRadPerGrid` 按分段表**量化**，带边界上会跳一档。必须沿 x 积分（0.25 格步长，单格误差 < 1 mm 量级）。
3. **"各自积分到节点、再 IEEERemainder 折返"** —— 证伪。整球图上"从参考经度走到某节点"的经度很容易越过 ±π，两侧各自取模后那道缝会落到两个相邻节点之间，把 1 m 算成 225 m。正确做法是**只在两点之间积分、完全不取模**。
4. **`Max(0, |纬度/0.36°| − 0.1)` 截断**（照抄游戏时的笔误）—— 证伪。游戏的 `GetSnappedLatitudeGridIdx` 是**取整之后**才取绝对值，没有 −0.1。南半球影响最大：−18.6° 被算成 20 格/圈（游戏是 1000 格/圈），1 m 的相邻链节虚报成 47 m。
5. **"试算省带量时按空间分块抽稀"** —— 证伪。分块会把整条链整段删掉，相对收益与全量跑严重不符（16.4小火箭 从 157 掉到 36，纬度搜索因此选错位置）。已改为不抽稀。
6. **"用几何最紧/最保守的纬度当默认值"** —— 证伪。省带量随纬度**强烈非单调**（16.4小火箭：76° 省 152、46° 省 0）。必须用实测省带量当目标函数。
7. **上一版遗留："原件超限的链节都是派生连接、可以直接丢弃"** —— 部分成立但要用**格位跨度**判定而不是 index 对。Optimize 对被删节点只做**引用改指**、不改几何；一条"改指"的链节超限，说明原件本来就在这个位置有同样长的跨度（实测 1080 三条 2.45~2.52 m 的链节，`原件同跨度=True`）。

### 保留（已在上一轮验证有效，未回退）

- 被分拣器/建筑引用的带节点固定、引用不改指；定点保护"该节点 + 后继 + 前驱"。
- 合并后仍跑 `InserterBinder` 逐端点判定/重绑。实测全部蓝图 **空端 0、悬空 0**。
- 跨纬带蓝图的"越限邻域固定"守卫（`pinOverLimit = calibration.MultiBand`）。
- `BeltWindowRepair` 仍停用（1.414 m 是"连接缺失时就近接上"的窗口，不是已存连接的判据）。
- `BeltPathOptimizer` / `InserterBinder` / `BeltPathGeometry` 的逻辑未改动。

## 4. 铁律分别是怎么被保证的

### 铁律①：绝不出现"过长而无法粘贴"的传送带（`sqrMagnitude > 5.3`）

1. **模型与游戏逐点同式**：经度沿 x 积分（逐节点查游戏自己的分段表）、纬度 `refLat + sign·y·0.36°`、半径 `z·1.3333 + 0.2 + realRadius`、判据就是游戏那一个 `sqrMagnitude > 5.3`。位置来自粘贴工具时误差为 0。
2. **优化上限带 2% 安全余量**（`cap × 0.98`，硬上限处约 4.6 cm），只用来吸收蓝图坐标的 float 截断与游戏端浮点累积。
3. **交付前自检**：`VerifyHardLimit` 逐条复核合并结果的每一条带-带链节；只要有一条 > 2.3022 m 就**放弃本次省带、保留原件**并在日志里写明。
4. **位置变化后的增量复核**：玩家移动/旋转粘贴位置时，先按新位置把现有结果量一遍（O(链节数)）；不过关才从**原件快照**重新省带；重算也失败就把原件放回粘贴工具——任何时刻都不会把"会被游戏拒绝"的蓝图交给玩家。

### 铁律②：绝不出现分拣器失效（`UIInserterWindow` 输入端/输出端失效）

1. 被分拣器/建筑引用的带节点**固定**，引用**不改指**。
2. 定点保护"该节点 + 后继 + 前驱"三点（分拣器总依附在一节带的起始处，局部路径只依赖这三点）。
3. 合并后仍跑 `InserterBinder` 逐端点判定/重绑；机器端永不触碰。
4. 离线判据：全部蓝图、两种位置 **空端 = 0、悬空引用 = 0**。
5. **注意**：离线判据与玩家在 `UIInserterWindow` 里看到的"输入端失效/输出端失效"不完全等价（游戏还会拒绝已存连接）。本版只改长度模型、没动连接重绑逻辑，**理论上不会比 73728 那版（已由玩家实测确认零失效）更差，但必须由玩家在游戏里复验**。

## 6. 遗留风险（明确写出）

1. **单区域蓝图无法反解"原始纬度"**：`tropicAnchor` / `anchorLocalOffsetX/Y` 全为 0，文件里没有绝对纬度。所以"按原始纬度"落地为"按蓝图库场景挑出的最佳合格纬度 + 粘贴时按真实位置重算"。**默认纬度是猜测，不是事实**；粘贴位置一旦到手就会被覆盖。
2. **蓝图库场景仍有一次性搜索代价**（6k 约 85 ms，3000 条带以内可接受）。若日后遇到 > 8000 条带的图，需要把 1° 网格改成 2° 网格或减少复核候选数。
3. **多区域蓝图的区域参考经度用的是"区域参考纬度处的格宽"**（游戏是逐节点值）。6k 这类"区域锚点与节点同带"的图误差可忽略；若某个多区域蓝图的节点跨很多带，跨区域链节的经度会有偏差，需要单独处理。
4. **正交接缝上的极少数链节**：模型对"绕完整整一圈"的链节（|Δ经度| ≥ 2π）不做折返，会算出很大的距离。这类链节本来就不可能是相邻带，但如果某张图真有"接缝两侧相邻"的带对，会被误判为超限而不敢合并（保守，不会出事）。
5. **`【极地】5发射+102弹射` 与 `2880太阳帆` 收益仍然很低**（0 与 6）：它们的相邻带跨度本身就贴着硬上限，能合的空间很小。这是几何事实，不是 bug。
6. **分拣器铁律的离线判据不等于游戏判据**（见 §4 铁律②第 5 点），必须玩家复验。
7. **`1080传送带+360分拣器` 在 81° 锚点下原件本身有 3 条 2.45~2.52 m 的链节**（`原件同跨度=True`，即原件里就有）。这属于"整球图派生连接"那一类，与本次改动无关；玩家若在这类图上看到红色报错，那是原件本身的问题。

### 8.1 v3 在游戏内会废掉 6k 这类图的省带（已修）

v3 的 `VerifyHardLimit` 把合并结果里**全部**越限链节都算作失败。而 `--regress` 的「越限链节(全部)」列早已说明：6k 在两种位置下有 34~47 条**原件同跨度**的越限链节。也就是说，v3 在游戏里点 6k 的「省带」，自检必然不过 → 放弃省带 → 省 0，与本文 §3 的离线表（219/227）矛盾。离线表没暴露这个问题，是因为回归台自己的复核按「原件同跨度」剔除，而插件路径没有。

v3.1 的口径：按原件 (区域,x,y)→(区域,x,y) 格位跨度建索引（量化 1/8192 格），`VerifyHardLimit` 只统计**新造跨度**；原件同跨度的越限记 `KeptOver`，日志单列（「原件同跨度越限 N 条」），不触发放弃。依据：游戏对原件的这些存储连接同样拒绝（见 8.3），合不合并那几节带都一样，省带没有让任何一节带变得更差；因它们放弃整次省带属于误伤。快照反解失败时索引为 null，退回旧的"全量保守"口径。

### 8.2 拖动流程的快照一次性消费（已修）

### 8.3 接缝与派生连接：本轮查清的两个事实

1. **「接缝绕整圈不折返」的前提不成立**。`CoreDistance` 最后用 sin/cos 构造 3D 坐标取弦长，经度差天然按角度周期折叠。极地图 226.06 m 的诊断值与折叠模型手算吻合。本文 §7 第 5 条描述的机制不存在，也**没有**因此损失省带量。
2. **真实接缝效应**：蓝图 x 坐标的周期是"拷贝时刻的分段数 ×5"，而节点在粘贴纬度处的一圈格数由节点自己的纬度带决定。两者不一致时（如 6k 的接缝节点在 38° 锚点下落在 800 格/圈的第 2 带，周期却是 600 格），接缝两侧的节点真实相距 90°（模型 214 m），游戏对这些带的粘贴检查同样拒绝。`--latsweep` 证明 6k 的接缝节点 y 跨 33.7°，**不存在让全部接缝对折回 1 圈以内的粘贴纬度**——这 47 节带是原件自带的，玩家粘贴 6k 时游戏本就会对它们报「距离太远」（只影响那几节，其余照常放置）。库模式因此正确回退到赤道 0°（省 227，最保守兜底）。
3. **派生连接（原 §7 第 6 条待研究）已查清**：`BuildTool_BlueprintPaste` 2083~2098 行对每条带→带存储连接查 `sqrMagnitude > 5.3`（TooFar）与陡度；`RefreshBuildPreview` 1541 行把 `outputObj` 原样映射进预览。极地图原件 #470→#469 确实存着 Δx=-5.55 格（任何纬度 ≥5 m）的连接——是蓝图作者侧遗留的断损段，游戏粘贴本来就拒绝那几节带，与 MOD 无关。

### 8.4 `BeltLinks` 的接缝证据（v3.1 新增）

证据链节在 `|Δx| ≤ 1.6` 之外，增加"同区域且 `|Δx| ≈ 整圈周期 ± 1.6`"的接缝对（y 仍要求 ≤ 1.6）。距离不在这里算：每个锚点纬度下由 `FramesSuggestLegal` / `OriginalFitsAt` / `Resolve` 的证据复核用折叠弦长判定——合法纬度上接缝对折回 0.2~1.7 m，非法纬度上保持巨大，库模式的默认纬度因此只会落在整张蓝图自身粘得上的窗口；没有这种窗口时回退赤道 0°。

### 9.1 为什么保点模式到不了 600

保点模式只能保留原节点子集，而相邻两条跨度受优化上限 2.254 m 约束：纬度方向 1 格 = 1.2566 m，**2 格跨度 2.5132 m 永远超限**，所以均匀 1 格直链一节都合不掉。16.4 的 152 全部来自曲线/亚格距段。这是数学上限，与模型精度无关。插值模式按弧长把链重排为 `ceil(长度/上限)` 个跨度，均匀直链可省 ~44%。

### 9.2 v3.2 的做法与安全链
